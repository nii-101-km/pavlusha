# Physical keyboard input verification

Local artifact paths below are generalized as `/path/to/dogfood`; the artifacts are not shipped in this repository.

On 2026-10-07, the public `agent.py` path ran the local vision-capable Worker
`qwen/qwen3.8-27b` against a copy of the latest Dungeon of Keys game.
All actions were generated by the real Worker: no scripted responses, injected
application events, forced moves or runtime/provider patches. `observer.py`
passively wraps pygame event retrieval and the original event handler, recording
KEYDOWN/KEYUP, scancodes, monotonic timestamps and before/after player positions.
The original and copied `main.py` have the same SHA-256:
`4040199580055f13d5647f335a4e25af29379d72d1a592a9947da3e120af7036`.

Local artifacts (outside the source distribution):
`/path/to/dogfood/scratch/gui-keyboard-dogfood-20261007/`:

- `command.txt`: exact CLI argv and task; `stdout.log`: real Worker reasoning/actions.
- `work/observer.py`, `work/main.py`, `work/evidence.json`: observer, unchanged game,
  actual application events and movement evidence.
- `measurements.json`: paired event durations and position changes.

The controller command was `.venv/bin/python /tmp/run-keyboard-dogfood.py`;
its subprocess used `.venv/bin/python agent.py --workdir .../work --state-dir
.../state --model qwen/qwen3.8-27b --worker-context-budget 40000
--reasoning-effort low --max-tokens 1600 --max-steps 16 --no-interactive` plus
the task saved verbatim in `command.txt`. GUI remained enabled through the normal
default. Worker launched `/work/.venv/bin/python /work/observer.py` with
`gui_start`, `network:false`; it received fresh screenshots after keyboard input,
read `evidence.json` through ordinary shell, compared actual positions, closed
the GUI and reached FINISH with exit code 0.

The first hold reached the application but was blocked by a wall. Worker noticed
this in the evidence, returned to a free row and repeated the hold successfully.
This distinguishes successful input from successful movement. Both requested
movement forms have application evidence, including key release. This is a
small control smoke, not a game completion test.

The separate real private-X11 regression switches to Russian layout, checks
physical `w` down/up (X keycode 25), Ctrl+L ordering, measured hold duration,
released query-keymap state after success and timeout, and unchanged W keymap.
It also checks that existing `type_text` still uses its temporary text keycode.
Unit tests cover schema/Core rejection, bounds, interruption/signals, partial
press failure, failed release, parent cleanup retry and fresh screenshot dispatch.

Limitations: physical input preserves position, not a translated Latin symbol.
An application using layout-dependent key symbols may still interpret W as `ц`;
the action never changes the layout. This game handles movement once per
KEYDOWN, so a 0.5-second hold moves one tile; continuous movement requires
application repeat/held-state handling. Event timestamps are sampled at the
game's ~60 Hz poll boundary, hence small differences from requested duration.
