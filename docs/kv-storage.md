# Хранилище KV-кэша при временной выгрузке модели

Упоминаемые ниже материалы `diagnostics/` относятся к локальным экспериментам
и хранятся вне репозитория, в каталоге разработчика `pavlusha-dev`.

Настройка относится к нашему Python-адаптеру `pavlusha_agent/llama_server.py`,
который управляет собственным llama-server. Исходники и бинарник llama.cpp,
контракт модулей, runtime и системный промпт не менялись.

В JSON-конфигурации сервера:

```json
{
  "argv": ["/absolute/path/llama-server", "--model", "/absolute/path/model.gguf"],
  "preserve_kv": true,
  "kv_storage": "ram"
}
```

- `preserve_kv: false` (по умолчанию): сохранение KV выключено.
- `preserve_kv: true, kv_storage: "disk"`: прежний временный каталог Python;
  на этой машине `/tmp` находится на ext4/NVMe. Это также значение по умолчанию
  для kv_storage, чтобы старые конфигурации сохранили прежнее поведение.
- `preserve_kv: true, kv_storage: "ram"`: приватный временный каталог в `/dev/shm`.
  Адаптер проверяет, что файловая система — tmpfs. Если она отсутствует, недоступна
  для записи или не tmpfs, запуск завершится ошибкой без перехода на диск.

RAM-режим использует штатное файловое API save/restore слота llama.cpp, но файл
размещается в оперативной памяти. tmpfs подчиняется системной политике swap;
этот режим не является запретом ОС использовать swap.

В проведённом эксперименте выбран RAM-режим.

В эксперименте использовался `--checkpoint-min-step 256` для гибридной модели.
Это увеличивает частоту контрольных точек рекуррентного состояния и позволяет
переиспользовать больше контекста между ходами. В догфуде 28 октября при пятом
ходе сервер повторно обработал 624 токена за 1,13 с вместо 2048 токенов за
2,50 с с прежним интервалом 8192. Каждая точка этой модели занимала около
150 МиБ; до 32 точек могут требовать около 4,7 ГиБ памяти. Это наблюдение для
конкретной модели и короткого прогона, а не гарантия для других задач.
Журналы: `diagnostics/cache-check/verbose.server.log` и
`diagnostics/cache-check-improved/session.server.log`.

Порядок выполнения не меняется: сохранить KV → выгрузить сервер → выполнить
команду → загрузить сервер → восстановить KV. Неудача сохранения не разрешает
выполнение команды. Восстановление проверяет число токенов и байтов. После него
снимок удаляется; после завершения запуска удаляется весь временный каталог.
История остаётся у контроллера независимо от KV. Наличие полного снимка не означает,
что следующий запрос использует каждый его токен: сервер переиспользует совпавший
префикс и обрабатывает изменившуюся часть запроса.

## Управление из дочернего процесса

Экспериментальная сборка поддерживает `--enable-server-control` для управляемого
сервера с включённым `preserve_kv`. Она создаёт локальный управляющий сокет в
каталоге KV. Дочерний процесс подключается через `--server-control-path` и получает
тот же каталог через `--kv-storage-dir`. Его `shell_released` просит владельца
остановить и снова запустить сервер. Включайте режим только для доверенных процессов.
Модуль оркестрации передаёт эти параметры младшему при запуске; общий сценарий
и результаты проверки описаны в [orchestration.md](orchestration.md).
