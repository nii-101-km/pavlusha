# Project State через интерфейс событий

Упоминаемые ниже материалы `diagnostics/` относятся к локальным экспериментам
и хранятся вне репозитория, в каталоге разработчика `pavlusha-dev`.

Экспериментальная сборка запускается через `project_state_agent.py` с теми же
аргументами, что `agent.py`, плюс `--review-every N` (по умолчанию 10;
0 отключает периодический review). Обычный `agent.py` не изменён.
При последующем добавлении восстановления расширены два файла ядра;
системный промпт сохранён.

## Состав сборки

`pavlusha_modules.shell.Shell` через публичный интерфейс BasicHost предоставляет
только `shell`. `pavlusha_modules.project_state.ProjectState` предоставляет
`project_init`, `project_update`, `project_review_complete` и `finish`.
Владельцем `finish` является State: незавершённые пункты возвращают
`unfinished_work`, а работа через shell продолжается. Завершённый план позволяет
вернуть `Outcome(..., controls=(Control('stop', summary, finished=True),))`. Отдельного реестра функций нет.

Это выбор состава приложения: State не перехватывает чужие функции. Если
подключить полный BasicHost вместе со State, две декларации `finish` вызовут
предусмотренную интерфейсом ошибку конфликта. Произвольный другой модуль,
возвращающий `Control('stop', ..., finished=True)` из своей функции, State сейчас блокировать не может.

## События и вклады

- `session_started`: State загружает своё состояние и проверяет принадлежность
  задаче и технической сессии. До инициализации доступен только `project_init`.
- `prepare_turn`: запоминает номер предстоящего тюрна; при новой эпохе контекста
  обновляет префикс State и handoff. Обычные изменения видны в результатах функций
  и истории; префикс внутри эпохи остаётся стабильным.
- `turn_completed`: получает полный тюрн, считает выполненные операции других
  модулей и при необходимости запрашивает review. Повторное событие того же
  тюрна не увеличивает счётчик.
- `before_reset`: требует свежую контрольную точку с handoff. До её получения
  выставляет `reset_ready=False`; обычный сброс откладывается.
- После review, затребованного для сброса, State возвращает отдельный `Control('reset', reason)` в EventReply.
  Ядро рассматривает запрос перед следующим тюрном и опрашивает готовность всех
  модулей через существующее событие `before_reset`.
- При обязательном сбросе из-за переполнения State восстанавливает последний
  чекпоинт в `before_reset` и разрешает сброс. После перезапуска с сохранённым
  чекпоинтом State также восстанавливает его и просит сбросить историю контекста.
- Во время review исключительный вклад оставляет только `project_update` и
  `project_review_complete`. Shell в этот момент недоступен. Завершение review
  сохраняет контрольную точку и снимает исключительный режим.
- `reasoning_fragment` и `session_stopped` пока не требуют действий State.

Исключительный режим скрывает вклады остальных модулей; исходная задача,
системные правила и техническая история остаются под управлением ядра.
При запрете другого модуля обязательный сброс останавливается с ошибкой и история
сохраняется. Если на перезапуске другой модуль отклонил сброс, State не позволяет
продолжить с восстановленным State и старым контекстом. Повторное переполнение с
тем же чекпоинтом останавливает работу, чтобы исключить бесконечное восстановление.

## Совмещённая проверка

Экспериментальная настройка модуля `{"combined_review": true}` делает
`project_review_complete` единственным доступным действием при обязательной
проверке. В нём можно передать `changes` (в том же формате, что у
`project_update`) и обязательный `handoff`. Изменения и handoff сохраняются
вместе; ошибка в любом из них не завершает проверку и не применяет изменения.
Результат предыдущей команды уже виден модели. По умолчанию режим выключен,
поэтому существующие сборки сохраняют прежний протокол.

## Хранение и восстановление

По умолчанию модуль хранит `modules/project_state/state.json` внутри каталога
технической сессии. Там находятся State, счётчики, последний обработанный тюрн,
причина review и последняя контрольная точка State + handoff. Запись атомарная,
с синхронизацией и SHA256 содержимого. После перезапуска модуль сам восстанавливает
семантическое состояние. Ядро восстанавливает техническую сессию.

После каждого обработанного тюрна модуль сохраняет поколение состояния с номером
тюрна; хранятся три последних поколения. Если основной файл повреждён или отсутствует,
модуль выбирает последнее подходящее поколение с корректным хешем и идентичностью.
При запуске он запрашивает у ядра завершённые тюрны после своего номера, применяет
их результаты и сохраняет состояние с новой позицией. Успешные изменения Project State
восстанавливаются по сохранённым результатам, команды повторно не запускаются.
Если поколений или необходимых тюрнов нет, либо результат изменения состояния
неизвестен, восстановление останавливается с ошибкой. Старые сессии без сохранённой
полной последовательности тюрнов таким способом восстановить нельзя.

Общей физической транзакции технической сессии и файлов модуля нет. Ядро записывает
результат тюрна в журнал до фиксации технической сессии и рассылки события; модуль
сам сверяет свою позицию с журналом. При обычном перезапуске без пропущенных событий
сохраняется прежнее восстановление checkpoint; при откате поколения или догонянии
журнала восстановленное состояние сохраняется и запрашивается сброс контекста.
Если процесс прервался во время выполнения функции и её результат
неизвестен, техническая сессия отказывается автоматически продолжать: действие
могло уже изменить файлы. Нужна ручная проверка, чтобы избежать повторного эффекта.

## Проверка и оставшееся препятствие

Тесты модуля проверяют инициализацию, review, изоляцию, handoff и сброс,
перезапуск, дедупликацию, отказ при повреждении данных, запрет раннего finish
при доступном shell, восстановление и защиту от повторного переполнения.

Догфуд восстановления с реальной Qwen3.8-27B: процесс аварийно завершён после
записи второго тюрна и до доставки его Project State. Затем основной файл состояния
намеренно повреждён, сохранено только начальное поколение. Модуль восстановил
инициализацию и позицию 2 из журнала; модель продолжила и завершила задачу на
8-м тюрне. Прерванный после записи тюрн содержал проверку наличия файла, а не
команду с изменением файлов. Проверка изменения файла и неизвестного результата
команды при аварии в этом догфуде не проводилась. Сценарий:
`diagnostics/state_recovery_dogfood.py`.

Настоящая модель завершила задачу в `../../state-dogfood/` за 9 тюрнов с двумя
сбросами: создала файл, проверила точные байты через Python, обновила State,
дважды сохранила review/handoff и завершила работу через State.

Служебное сообщение теперь не утверждает, что State отсутствует. Модель ориентируется
на активные инструкции модулей и схему доступных функций.
