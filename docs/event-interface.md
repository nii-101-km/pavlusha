# Интерфейс событийного ядра, версия 2

Ядро не знает структуры Project State, правил review и устройства Project Map.
Системный промпт сохранён.
Пользовательские функции прежнего FunctionRegistry и мост истории не возвращаются.

## Четыре части контракта

1. **Event** сообщает, что произошло.
2. **Contribution** описывает контекст модели, доступные инструменты и ограничения.
3. **Control** просит ядро выполнить переход состояния.
4. **Tool / InvocationContext / Outcome** описывают выполнение инструмента.

Код контракта: `pavlusha_agent/extensions.py`, `MODULE_API_VERSION = 2`.
Сборка передаёт объекты в `Runtime(extensions=[...])`; загрузчик фабрик описан в
`module-loader.md`. Модуль имеет уникальное `name` и метод `on_event(event)`.

## События

| Событие | Когда | Данные |
| --- | --- | --- |
| session_started | При запуске процесса | task, resumed, session_dir, last_turn_id |
| prepare_turn | Перед сборкой запроса | next_turn_id, first_in_context, reset_reason |
| reasoning_fragment | Во время генерации | text, fragment_index |
| key_pressed | При обработке нажатой клавиши | key |
| paused | На безопасной границе, когда можно запросить ввод | reason, require_message, key |
| turn_completed | После сохранения тюрна | turn: запрос, полный/частичный ответ, действие, результат, статус, принятые controls/observations инструмента |
| before_reset | Перед попыткой сброса | reason, mandatory, history |
| session_stopped | При выходе из запуска, включая паузу | reason, error |

Event содержит session_id, turn_id, context_epoch и data. Каждый обработчик получает
свою копию. У reasoning_fragment turn_id — генерируемый тюрн, у остальных событий —
последний сохранённый. Фрагменты и нажатия клавиш не пишутся отдельно в долговечный журнал; полный
или прерванный ответ сохраняется в тюрне. События автоматически при перезапуске не переигрываются.

Модуль может объявить `bind_event_journal(read_turns)`: ядро передаст функцию
`read_turns(after_turn)`, возвращающую копии сохранённых завершённых тюрнов строго
после указанного номера, по порядку. Ядро обнаруживает пропуски и повреждения
журнала; в этом случае функция сообщает ошибку. Модуль сам хранит позицию и решает,
нужно ли ему восстанавливать свои данные. Технический журнал может содержать и другие
события, но их выборочное восстановление через этот интерфейс пока не предусмотрено.
Результат тюрна записывается в журнал до фиксации технической сессии и рассылки
`turn_completed`. Если действие прервалось с неизвестным результатом, восстановление
сессии по-прежнему блокируется без автоматического повтора действия.

## Ответ обработчика

```python
return EventReply(
    contribution=Contribution(
        prefix={'snapshot': 'Снимок модуля'},
        message='Текущая инструкция',
        tools=(my_tool,),
        exclusive=False,
        reset_ready=True,
    ),
    controls=(Control('reset', 'checkpoint ready'),),
)
```

`contribution=None` сохраняет прежний вклад; новый Contribution заменяет его целиком.
Пустой Contribution снимает вклад. Для ответа только со вкладом разрешён короткий
`return Contribution(...)`; `return None` ничего не меняет. Контрольные запросы
не входят во вклад и не исчезают при его замене. Запрос сброса остаётся в очереди
до успешного сброса. `request_reset` удалён из Contribution.

`exclusive` ограничивает доступные инструменты инструментами владельца режима.
Префиксы, сообщения и наблюдения остальных модулей сохраняются в запросе;
события по-прежнему доставляются всем модулям.
`reset_ready=False` откладывает сброс. При фактическом переполнении и отказе
готовности ядро останавливается без удаления истории.

Одинаковые имена модулей/инструментов, включая скрытые инструменты, запрещены.
Два владельца exclusive и отсутствие доступных инструментов — явные ошибки.
Снимок схем, обработчиков, владельцев и политик выполнения фиксируется на запрос.
Обновления во время генерации действуют на следующий запрос.

## Управление

| Control | Действие ядра |
| --- | --- |
| reset | Попытка сброса перед следующим тюрном с before_reset и проверкой готовности |
| interrupt | Прервать генерацию; допустим только из reasoning_fragment |
| stop | Остановить запуск с reason; finished=True означает окончательное завершение задачи |
| pause | Сохранить вопрос reason и приостановить запуск до пользовательского ответа |

reason — обязательная непустая строка. finished разрешён только для stop.
В одном ответе запрещены несколько stop/pause. Между модулями stop имеет приоритет
над pause; обычная остановка имеет приоритет над отметкой finished. Несколько
одновременных пауз — ошибка. Это разрешение запросов управления, а не механизм
предметных возражений против finish; последний остаётся отложен.

Control разрешён также в Outcome инструмента, кроме interrupt. Запросы принимаются
только вместе с корректным результатом, прошедшим лимит размера. Переполненный или
невалидный результат не приводит к выполнению controls и публикации наблюдений.

При interrupt провайдер получает False из потокового callback, закрывает соединение
и отдаёт частичный ответ через WorkerStreamInterrupted. Ядро сохраняет тюрн со
статусом generation_interrupted, action=None; никакой инструмент не вызывается.
Если провайдер вернул готовый ответ вопреки False, он тоже не выполняется.
Без stop/pause работа продолжается со следующего тюрна. Модуль `loop_detection` использует этот переход для обнаружения повторов рассуждения. Максимум тюрнов ограничивает
и последовательность прерываний.

Без интерактивного терминала при pause Runtime.run() возвращает вопрос, статус сессии становится paused, модули
получают session_stopped и освобождают ресурсы. Новый Runtime создаёт их заново;
продолжение требует user_input. Ответ сохраняется, переживает восстановительный
сброс State и попадает в запрос/историю как USER REPLY. Завершённое действие не
повторяется. В экспериментальной сборке ответ передаётся через --user-input;
в интерактивном режиме процесс ждёт ответ и продолжает работу без перезапуска.

## Интерактивное управление

Модуль с методом `bind_interaction(interaction)` получает ограниченный интерфейс:
`request_pause(urgent=False)`, `read_user_input(prompt, require_message=False)` и
`resume(message)`. Запрос ввода доступен при обработке события `paused`; он показывает
строку ввода и ждёт ответа. После ввода модуль явно вызывает `resume`: строка
становится сообщением пользователя для следующего тюрна, пустая строка продолжает
без сообщения, а `None` завершает сессию. События клавиш доставляются всем модулям,
в том числе при exclusive review. При открытом вводе клавиши обрабатывает терминал.

Обычная пауза ждёт окончания текущего тюрна и его действия. Срочная прерывает
генерацию и отбрасывает её неполный ответ и действие. Если выполнение действия уже
началось, обе паузы ждут его завершения и сохранения результата. Для потокового
провайдера прерывание проверяется при получении очередной строки ответа: если сервер
не присылает данные, ожидание может продлиться до ответа или тайм-аута.

Подключаемый модуль `interactive` назначает Ctrl+Z обычную паузу, Ctrl+\ — срочную;
после приглашения `PAUSED` вводится сообщение, Enter продолжает, `/quit` завершает
сессию. `ask_user` также открывает ввод в работающем процессе. В сборке терминал
включается автоматически при терминальном stdin; `--interactive` и `--no-interactive`
задают режим явно. При отключённом терминале сохраняется прежний выход из процесса
с последующим продолжением через `--user-input`.

## Вызов инструмента

```python
def invoke(arguments, context):
    current_reasoning = context.response['reasoning_content']
    return Outcome({'status': 'accepted'})
```

InvocationContext содержит session_id, turn_id, context_epoch и копию полного
ответа текущего тюрна. Runtime, провайдер и изменяемая история не передаются.
Это позволяет модулю реализовать запись кода из текущего рассуждения без отдельного
события перед выполнением. Модуль `reasoning_code` использует этот контекст для записи кода.

Сигнатура всех обработчиков теперь `(arguments, context)`. Outcome содержит result
(JSON-объект), controls и observations. Поля Outcome.stop/summary удалены.
Базовый finish и finish Project State используют Control('stop', summary, finished=True).
Семантические правила завершения всё ещё принадлежат Project State.

## Ресурсы основной модели

Tool.execution = ExecutionPolicy(release_model=True, restore_guard=callback)
фиксируется вместе с описанием инструмента. Без этой политики модель не выгружается.
Ядро использует существующий released_worker адаптера:

1. Записывает маркер ожидающего действия и освобождает модель.
2. Вызывает инструмент.
3. Сохраняет фактический результат и рассылает turn_completed.
4. Вызывает guard и восстанавливает модель.

Guard принадлежит доверенному модулю и подтверждает освобождение его ресурсов.
Ошибка guard/восстановления останавливает запуск. ProcessCleanupError передаётся
адаптеру: модель остаётся выгруженной, неопределённое действие сохраняет pending
и блокирует автоматический повтор. Ошибка входа в release не вызывает инструмент.
Политика не предоставляет shell доступ к GPU — разрешения песочницы независимы.
Модуль `gpu_shell` использует этот механизм для песочницы. Отдельный сервис
Transformers не подключён; GPU-задачу задают командой.

## Текстовые и визуальные наблюдения

```python
Observation(text='Текущий экран', image='data:image/png;base64,...',
            lifetime='next_request')
```

Observation принимается в Contribution и Outcome. Может содержать текст, картинку
или оба. Картинки — встроенные PNG/JPEG, без чтения host-путей и скачивания URL.
Ядро проверяет кодировку и сигнатуру типа; это не полный декодер изображения.
Вклад владельца помечается в сообщении; формат модели — text/image_url parts.

next_request расходуется при отправке следующего запроса, в котором наблюдение
видимо, включая запрос с ошибкой провайдера. Скрытое exclusive-наблюдение не
расходуется. until_replaced сохраняется до замены вкладом или следующим результатом
того же владельца соответственно. Новые наблюдения результата заменяют прежний
набор результатов этого модуля. В историю тюрнов изображения автоматически не
копируются: они остаются отдельными наблюдениями; журнал хранит их в результате
и в фактическом запросе. На перезапуске наблюдения должен восстановить модуль.

Лимиты: до 4 видимых наблюдений на запрос; текст каждого до 24000 символов;
закодированное изображение до 12 млн символов; суммарно до 16 млн декодированных
байт изображений. Превышение явно отклоняется. Поддержка изображений конкретной
моделью/сервером проверяется при подключении соответствующего модуля.

## Сохранение и очистка

Техническая сессия хранит историю, номера, pending и паузу. Модули хранят свои
предметные данные. before_reset идемпотентен; новая эпоха видна на prepare_turn.
Инициализация ресурсов — на session_started; очистка — на session_stopped в обратном
порядке, включая частично неудачный startup. Ошибка очистки одного модуля не
пропускает остальных; неочищенные владельцы сохраняются для явного повтора.

Этот рефакторинг не добавляет общей аварийной транзакции состояния ядра и модулей,
отката по поколениям или автоматического разрешения pending. Доставка событий и
переходов управления не становится exactly-once при падении процесса. Общие события
ошибок, обработчики перед finish и изменение системного промпта остаются отложены.
